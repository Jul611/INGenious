# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

INGenious is a Java/JavaFX no-code/low-code test automation IDE (Playwright-Java, Appium, JDBC, JMS/Kafka, SAP), built by ING Bank and open-sourced under MIT (`ing-bank/INGenious`). Full user docs: https://ing-bank.github.io/ingenious-doc/.

## Build & test

This is a multi-module Maven reactor. **`ingenious-api` is not a reactor module** — it's a standalone project that other modules (and all plugins) depend on with `scope=provided`, and must be built and installed to the local `.m2` cache *before* the main reactor:

```bash
mvn clean install --file ingenious-api/pom.xml
mvn clean install --file pom.xml
```

To iterate on a single module without a full reactor build (much faster), build it plus only its required upstream modules:

```bash
mvn -pl IDE -am compile -DskipTests
```

Other useful commands:
- `mvn test` — runs the Surefire test suite (JaCoCo coverage is wired into the same lifecycle).
- `mvn dependency-check:check --file pom.xml` — OWASP dependency vulnerability scan (CI runs this on JDK 11, specifically; the main build runs on JDK 17).
- `mvn versions:display-dependency-updates` — check for outdated dependency versions (`versions-maven-plugin` is available).

**Auto-formatting gotcha**: `prettier-maven-plugin` is bound to the `validate` phase with the `write` goal (see root `pom.xml`), which means **any `mvn` command that reaches `validate` — including a plain `compile` — silently reformats every Java file it touches in place.** If you write/edit a file and then run a Maven command, expect the file's exact byte content (indentation, line-wrapping of long expressions/string concatenations) to change afterward. This breaks exact-string-match tools (e.g. an `Edit`-style diff) if you re-match against what you originally wrote rather than the post-format state — re-read the file (or use line-number/regex-based replacement) after the first `mvn` invocation touches it, not before.

## Module structure

- **Common** — shared build-lifecycle helpers/config for the reactor.
- **Datalib** — backend data source access, data retrieval/transformation.
- **Engine** — core business logic and test-execution workflows; also owns plugin *loading* (`Engine/src/main/java/com/ing/engine/plugin/loader/`).
- **IDE** — the Swing/JavaFX desktop IDE itself; almost all user-facing feature code lives here, under `IDE/src/main/java/com/ing/ide/`.
- **StoryWriter** — BDD scenario/feature authoring.
- **TestData - Csv** — test data / test plan orchestration.
- **Dist** — assembles the final packaged distribution (zip) from the other modules' outputs.
- **ingenious-api** (root-level, non-reactor) — the public contract plugins compile against.

## Code conventions

4-space indent, ~120-char lines, braces always (even single-statement blocks), `PascalCase`/`camelCase`/`UPPER_SNAKE_CASE`. Prefer collection interfaces (`List`, `Map`) over concrete types, Stream API for filtering/mapping, `final` where applicable. INGenious action-naming conventions: storage actions are `store<Data>In<Target>` (e.g. `storeDBValueInDataSheet`), assertions are `assert<Object><Condition>` (e.g. `assertResponseBodyContains`).

The stated convention is no wildcard imports — in practice, existing files (e.g. the whole `pluginmanager` package) use `import java.awt.*;`/`import java.util.*;` throughout. Match the surrounding file's existing import style rather than enforcing the stated rule against it.

## Plugin Marketplace (in progress)

Lives under `IDE/src/main/java/com/ing/ide/main/mainui/components/pluginmanager/`. Lets plugin authors submit a plugin via fork+PR against a separate GitHub registry repo, and lets any user browse/install published plugins — all without ever storing a GitHub PAT: `git`/`gh` manage their own credentials (HTTPS+Git Credential Manager, `gh auth login`), and the IDE never touches either directly for auth.

**Flow**: contributor points Publish at their plugin's source — primarily a GitHub repo+branch link (`cloneContributorSource()` shallow-clones it into a temp dir), or a local folder for quick iteration before pushing anywhere — IDE builds it locally either way to extract manifest metadata and discover actions via reflection → on submit, forks-or-branches the registry repo (based on actual write-access via `gh api .../permissions.push`, not on repo ownership) → opens a PR. A human reviews and merges. CI then independently builds the real artifact, `mvn deploy`s it to an Azure Artifacts Maven feed, and patches the registry via its own auto-merged PR. Install resolves the jar + transitive deps from that feed via Maven.

Contributors are also expected to run their own build+validate pipeline (`docs/plugin-contributor-pipeline-template/`) against their own repo *before* ever pointing Publish at it — but this is a courtesy pre-filter, not a trust boundary the marketplace relies on. The marketplace's own `validate-pipeline.yml` always independently re-builds and re-checks the same source after the PR is opened, regardless of what the contributor's own pipeline already reported, since the marketplace is the one taking the action of deploying to the shared feed afterward and can't base that on a contributor's self-reported pass. This is why the two pipelines' checks are near-identical by design, not an oversight to deduplicate.

**Key files**:
- `MarketplaceCliService` — all `git`/`gh`/`mvn` process-shelling: fork/branch resolution, PR submission, registry reads, Maven artifact/dependency resolution, `cloneContributorSource()` (read-only shallow clone of a contributor-supplied repo+branch, for the Publish tab's repo-link input — no fork resolution or push, unlike `submitPlugin()`'s own clone of the registry repo), and `saveAdoCredential()` (writes a user-pasted ADO PAT into their real `~/.m2/settings.xml`, preserving anything else already there). `GH_OWN_GIT_CREDENTIAL_ENV` hands gh's own already-verified git credential helper to every network git op in the submission flow — clone, push, and `gh pr create`'s own internal git use — via a scoped `GIT_CONFIG_COUNT` env override (not a persisted git-config change), so the flow depends on exactly one credential source instead of also trusting git's separate credential helper (e.g. GCM) to be configured correctly on the user's machine; the older soft `gh auth setup-git` suggestion is gone now that this is unconditional. `submitPlugin()`'s branch push is `git push --force`, not a plain push — the per-submission branch name (`plugin/<name>/v<version>`) is deterministic, so resubmitting the same plugin+version (routine during manual testing) would otherwise fail as non-fast-forward against the leftover branch from the prior attempt; against a real shared registry with outside contributors, this would also silently clobber any manual follow-up commit someone pushed straight to that PR branch.
- `MarketplaceConfig` — hardcoded constants (registry repo/branch/path, Maven groupId, ADO org/project/feed/server-id, plus the Reusable Components registry path/sub-path below) — there's exactly one real marketplace, so ordinary users never see or configure any of this; only the ADO PAT is a per-user input.
- `PluginRegistrySettingsDialog` — the config UI, plus a write-only ADO PAT field and a live git/gh/mvn/ADO-credential status panel.
- `PluginManagerService` / `PluginManagerPublishUI` / `MarketplaceBrowseUI` — orchestration and the Publish/Browse tab UIs. Publish's Step 1 offers the repo+branch link as the primary input (backed by `cloneContributorSource()`) with local folder browsing kept as a secondary option; both converge on the same `selectedSourceDir`-based build/metadata/staging flow afterward, so nothing downstream needed to change.
- `docs/plugin-registry-template/` — a copy-paste template for whatever repo ends up being the real registry, plus its own setup README. **GitHub Actions hosted runners are not available for this org** (confirmed via a hard error, not just a preference) and installing the Azure Pipelines GitHub App yourself isn't allowed either (that's an org-admin action, done automatically for repos created within the company) — so the `.github/workflows/validate.yml`/`publish.yml` pair is kept only as reference; the CI actually in use lives in `ado-pipelines/` (`validate-pipeline.yml`, `publish-pipeline.yml`, `cleanup-stale-branches-pipeline.yml`), triggered by Azure Pipelines' native GitHub PR/push integration instead. `ingenious-api` is deliberately *vendored* as a jar in this template (`ci/vendor/`) rather than resolved from ADO, specifically so the PR-time pipeline stays credential-free to safely build fork-PR'd code — that reasoning holds regardless of which CI system runs it.
- `docs/plugin-contributor-pipeline-template/` — **active**, not parked (an earlier fully-decentralized design here — contributor pipeline does build+validate+publish, marketplace never builds at all — was considered and explicitly rejected: the marketplace still needs its own independent validate before it deploys under its own authority). What this template actually does now: build + the same checks `validate-pipeline.yml` runs (required files, README length, groupId, build, manifest), and nothing else — no ADO credentials, no feed access, no registry-repo/GitHub-App dependency at all. Runs entirely on the contributor's own repo/ADO project, decoupled from the marketplace's infrastructure. Its only purpose is catching obviously-broken submissions before they cost the marketplace a CI run or a reviewer's attention — passing it doesn't skip or shortcut `validate-pipeline.yml`, which always re-runs independently once the contributor submits via the IDE.

## Reusable Components Marketplace

Same submission mechanism as the Plugin Marketplace (same repo, same review-gated PR flow), deliberately simpler: a Reusable Component is just data (a Shared scenario's test-case YAML files — `Datalib/.../component/io/YamlTestCaseStore`), never compiled, so there's no build, no Maven coordinates, no version, and no Azure Artifacts feed at all — GitHub-repo-only, which is why this only needed a validate pipeline, no publish/deploy pipeline and no contributor-pipeline-template equivalent (the source is always already-local, never a separate repo+branch to pre-check).

**What's shared vs. new**: `MarketplaceCliService` gained two generalized methods so the actual git/gh mechanics aren't duplicated — `submitToRegistry()` (the fork/branch/PR submission mechanism `submitPlugin()` now delegates to, parameterized by target sub-path instead of hardcoding `plugins/`) and `fetchFileFromRegistry()` (same generalization for `fetchRegistryJsonRaw()`), plus a new `listRegistryDirectoryRaw()` (Reusable Components have no Maven artifact to resolve on install, so installing means listing and copying whatever files a component actually has). Everything Maven/ADO-shaped (`buildLocally()`, `resolvePluginArtifact()`, `saveAdoCredential()`, the groupId check) stayed exactly where it is — untouched, and not something a Reusable Component has an equivalent of.

**Key files**: `ReusableComponentEntry` (name/displayName/description/author/authorEmail/tags/dateAdded/featured — no `entryClasses`/Maven coordinates/version) · `ReusableComponentCliService` (thin — composes `MarketplaceCliService`'s generic methods) · `ReusableComponentService` (mirrors `PluginManagerService`'s shape: `fetchRegistry()`, `listLocalSharedComponents()` for the Publish picker, `stageSubmission()`, `installComponent()`) · `ReusableComponentPublishUI` (the Publish form/panel — see below for where it's actually mounted) · `SharedReusablePopupMenu` (`SharedReusableTree.java`) — "Publish to Marketplace..." on a right-clicked scenario, visible only in the scenario context, opens `ReusableComponentPublishUI.openInDialog()` pre-selected on that component.

**UI placement — one Marketplace window, not a second one**: `MarketplaceManager`'s existing Browse/Installed/Publish tabs host both artifact types now, not just plugins. Browse (`MarketplaceBrowseUI`) fetches and merges both `PluginRegistryEntry` and `ReusableComponentEntry` lists into one sorted, filterable card list (a `JComboBox` — All/Plugins/Reusable Components — plus the existing search box); each entry type still gets its own card class (`PluginCard` vs. the new `ReusableComponentCard` inner class) and its own install mechanism, only the container and filtering are shared. Installed's own table stays plugin-only, deliberately — a Reusable Component's "installed" state already lives in Test Design's own Shared Reusable Components tree, so a second table here would just duplicate it. It does show a component count alongside the plugin count at the bottom, though (`PluginManagerInstalledUI`'s two-`JLabel` status bar, count-only by design, no directory paths or other detail bundled in) — pure discoverability, not a second managed list. Publish is one tab with a type selector (`MarketplaceManager.buildCombinedPublishTab()`) swapping via `CardLayout` between `PluginManagerPublishUI` and `ReusableComponentPublishUI` — the two forms stay fully separate (no shared/conditional fields), only the navigation is unified. The context-menu path keeps its own focused standalone dialog (`ReusableComponentPublishUI.openInDialog()`) rather than routing through the main window, since that's a genuinely different use case (you already know what you're publishing).

Also removed this pass: the "Import from File..." local-JAR fallback button (`MarketplaceManager`'s old `importFromFile()`) — a leftover offline/demo path from before the marketplace was real, no longer needed now that install genuinely works end to end for both artifact types.

**The one real mechanical difference from plugins**: there's no merge-time bot pipeline for this artifact type to patch a registry file after the fact, so `reusable-components.json` gets updated *inside the contributor's own PR* (`ReusableComponentService.buildUpdatedRegistry()` computes it, `submitComponent()` commits it alongside the component's own files via `submitToRegistry()`'s `additionalFiles` param — a repo-root file living outside the component's own sub-path, committed in the same branch). Since that diff is contributor-supplied rather than bot-patched, `validate-reusable-component-pipeline.yml`'s last check exists specifically to verify it only adds-or-updates the submitter's own single entry — the thing that earns trust for a self-supplied registry edit that would otherwise be a plugin-side no-no (per CLAUDE.md's own "never trust self-reported data over what's actually verified" pattern elsewhere in this file).

**RC storage model, confirmed by reading the actual code, not just this doc**: a Reusable Component is a folder, `reusable-components/{name}/` in the registry branch, holding its YAML test-case files plus a `.component.json` sidecar (`ReusableComponentCliService.submitComponent()` → `submitToRegistry()`'s `targetSubPath`). Install is the mirror image, not a stub: `ReusableComponentService.installComponent()` lists that folder (`listRegistryDirectoryRaw()`) and copies each file down (`fetchFileFromRegistry()`, both real `gh api repos/.../contents/...` calls) into the local Shared Reusable Components folder.

**Three bugs found and fixed while finalizing this pass, all in code that had never been exercised end to end before now**:
- `MarketplaceBrowseUI.installComponent()` never called `onInstallCallback` on success, unlike `installPlugin()` — the Installed tab's component count went stale until the whole Marketplace window was reopened. Now calls it, matching the plugin path.
- `ReusableComponentPublishUI.submit()`'s `done()` only ran `cleanupClonedSource()` on the success branch, unlike `PluginManagerPublishUI`'s equivalent (which runs it unconditionally after the try/catch) — a failed submission (auth/network/PR-creation error) leaked the temp cloned-repo directory. Now cleans up regardless of outcome.
- The bigger one, in `MarketplaceCliService.submitToRegistry()` — shared by both `submitPlugin()` and `submitComponent()`, so this fix covers plugins too, not just RCs: it always `git push --force`s to a deterministic branch name, then calls `gh pr create`. A plugin's branch (`plugin/<name>/v<version>`) only collides on a same-version resubmission (rare). An RC's branch (`reusable-component/<name>`) has no version at all, so *any* resubmission of the same component — e.g. fixing a validation failure and submitting again, an entirely normal flow — reuses the identical branch name every time. Without a fix, the force-push would silently update the still-open PR's content, and then `gh pr create` would fail ("a pull request already exists"), reporting the *entire* submission as failed even though it had actually just updated the existing PR. Fixed by adding `findOpenPrForHead()`: before calling `gh pr create`, check `gh pr list --head <branch> --state open` (bare branch name — confirmed via `gh`'s own docs that `--head` doesn't accept the `owner:branch` fork-qualified form `gh pr create --head` does) and, if a PR is already open on that branch, return its URL directly instead of attempting to create a new one. A routine resubmission now cleanly reads as "updated my existing PR."

**Current state**: publish (opens a real PR) and browse (reads a real `registry.json`/`reusable-components.json`) have both been manually exercised end to end for plugins and Reusable Components alike, against the marketplace's own registry repo (working off a `registry-branch` rather than its default branch — repo identity itself is deliberately not tracked in this file, it's config, not architecture). Plugin install (resolves a real jar from ADO Artifacts) has also been manually confirmed end to end, against a real company ADO feed. RC install (the file-copy mechanism above) has not yet been manually exercised end to end — it's implemented and the three bugs above are fixed, but this pass was a code-level review, not a live test; that's the next thing to actually run. The CI pipeline piece (`ado-pipelines/`) has moved past placeholder values for `validate-pipeline.yml` and `publish-pipeline.yml`, and `publish-pipeline.yml` has been confirmed to run successfully end to end (GitHub App auth + deploy to the feed). `cleanup-stale-branches-pipeline.yml` stays deliberately disabled — see below.

**Known gotchas from manual testing**:
- **ADO Artifacts has no Maven-publish path via `az` CLI.** `az artifacts` only supports Universal Packages (a different, incompatible package type/protocol from what `resolvePluginArtifact()` resolves) — publishing a real Maven artifact only ever happens via `mvn deploy`, never `az`.
- **Two different ADO PAT scopes matter and are easy to conflate**: the one in `~/.m2/settings.xml` (managed by the app via `saveAdoCredential()`) is deliberately **Packaging: Read** only, for installs. A manual `mvn deploy` test needs a separate **Packaging: Read & Write** PAT under a different `<server>` id — trying to deploy with the read-only one fails with 401, by design, not a bug.
- **`-DaltDeploymentRepository=...` on the command line is fragile** across shells (line-continuation characters differ between bash/zsh and PowerShell; a dropped `-D` prefix manifests as a confusing "could not resolve plugin/artifact" error, not an auth error). For one-off manual deploys, temporarily adding `<repositories>`/`<distributionManagement>` to a *scratch copy* of the plugin's `pom.xml` sidesteps this — never commit that into `plugin-examples/helloworld/pom.xml` itself, since contributor plugin POMs are meant to stay infra-agnostic.
- **`ADO_FEED_SERVER_ID`-style values have to match in two separate, independent places — easy to conflate since both are called "server id" and both default to a similar-looking string.** (1) *Install side, in the IDE*: `AppSettings.ADO_FEED_SERVER_ID` (Registry Settings' "Maven server id (internal label)" field, default `ado-plugin-feed`) is used identically as the `<repository><id>` in the generated shim pom and in every `-DremoteRepositories=<id>::default::<url>` CLI arg (`MarketplaceCliService.resolvePluginArtifact()`/`resolvePluginDependencies()`). It only has to match the `<id>` of a `<server>` entry in the *user's own local* `~/.m2/settings.xml` (the one `saveAdoCredential()` writes) — it does **not** need to equal the real Azure Artifacts feed name; it's a purely local bookkeeping key, independent of Registry Settings' separate "Feed name" field. (2) *Publish side, in `publish-pipeline.yml`*: the `ADO_FEED_SERVER_ID` variable has to match whatever `MavenAuthenticate@0`'s `artifactsFeeds` input resolves to as a `<server><id>` — and `artifactsFeeds` is *not* a free label, it has to be the real feed's actual name in ADO, since that's what the task authenticates against. So inside that one pipeline, `ADO_FEED_SERVER_ID` == `artifactsFeeds` == the real feed name, or the deploy step's `-DaltDeploymentRepository` can't find matching credentials. These two matching-groups don't technically have to equal each other, but `publish-pipeline.yml`'s own inline comment recommends keeping the IDE-side value and the pipeline-side value identical anyway, purely so there's one string to remember instead of two.

**CI pipelines — architecture settled, wiring now mostly filled in**: GitHub Actions is unavailable outright (hosted runners disabled org-wide), so PR-time validate and merge-time publish both run on Azure Pipelines (`docs/plugin-registry-template/ado-pipelines/`), triggered via Azure Pipelines' own GitHub PR/push integration rather than `.github/workflows/`. A fully-decentralized alternative (contributor pipeline does build+validate+publish, marketplace never builds at all) was considered and explicitly rejected — see `docs/plugin-contributor-pipeline-template/` above for why the contributor template stays a courtesy pre-filter instead of replacing this centralized validate/publish pair.

Two things changed from the original GitHub-Actions-only design, beyond just moving where the YAML runs:
- The merge-time deploy step uses `MavenAuthenticate@0` + `$(System.AccessToken)` for the ADO feed (reusing the team's existing INGenious-build pipeline pattern) — no `ADO_PAT` secret to own/rotate.
- All GitHub-side write operations — the registry-patch push+PR in `publish-pipeline.yml`, the PR-listing+branch-deletion in `cleanup-stale-branches-pipeline.yml` — go through the **`GitHubAppToken@1`** task instead of a GitHub PAT, since a standing PAT for this isn't allowed. It exchanges the org's installed GitHub App connection for a short-lived (~1hr) installation token, consumed via `GH_TOKEN` for `gh` CLI calls. (This was previously unreconciled against an alternate name, `create-github-app-token@1` — `GitHubAppToken@1` is the one actually wired into `publish-pipeline.yml` now, with a real `githubAppConnection` value. `cleanup-stale-branches-pipeline.yml`'s dormant code has since been brought current with the same task name and `githubAppConnection` value, but the file itself is still fully commented out — see below for why.)

**Confirmed working**: `docs/plugin-registry-template/ado-pipelines/diagnostic-github-app-token-test.yml`, a throwaway diagnostic pipeline, ran end to end against a repo with the GitHub App connection enabled — the token task resolved, the `githubAppConnection` connection resolved, and the resulting installation token has both read and write access (verified by creating and immediately deleting a real branch via the GitHub API). This settled what was previously the biggest open risk in this design, and the resolved task name and a real `githubAppConnection` value have since been copied into `publish-pipeline.yml`, alongside a real `ADO_FEED_SERVER_ID` — and `publish-pipeline.yml` itself has since been confirmed to run successfully end to end (both the GitHub App auth and the feed deploy). `cleanup-stale-branches-pipeline.yml`'s dormant code has since been brought current (real task name and `githubAppConnection` value, matching `publish-pipeline.yml`), even though the whole file is still commented out end-to-end — deliberately disabled, matching an earlier ask to hold off on any branch-deletion pipeline. The diagnostic pipeline/file itself is disposable once `cleanup-stale-branches-pipeline.yml` is actually re-enabled.

The GitHub App connection is enabled automatically on repos **created within the company**, not on personal ones — this was the reasoning for testing the token mechanism against a separate company-created repo early on, back when the day-to-day registry repo was still a personal/workaround stand-in without that connection. That's no longer the setup: the registry repo in use now was made directly for the marketplace, not a personal fork, so this constraint no longer limits what's testable here.

**Checkmarx (SAST) — wired up, verified against the task's own source, and gated on severity.** `validate-pipeline.yml` is now two stages instead of one: `Validate` (everything it always did — structural checks + `mvn clean package` against the contributor's own pom.xml) and a new `SecurityScan` stage that `dependsOn: Validate` / `condition: succeeded()`, re-deriving its own `pluginName` from `git diff` rather than consuming one from `Validate`. **Why a separate stage:** stages get their own fresh agent/job, so the Checkmarx credential is never resolvable from the same process that runs `mvn clean package` on untrusted contributor code, and `Validate`'s own header stakes its fork-PR safety on holding no credentials at all. Reusable Components stay out of scope (nothing compiled to scan). This runs at PR-validate time, not merge/publish time — deliberately, so a finding blocks the PR before `publish-pipeline.yml` ever deploys the artifact to the shared feed, the same catch-it-before-it's-too-late reasoning the rest of this design already runs on.

The task is `CheckmarxAST@3`. Cross-checked against two independent sources — a real working pipeline in the same ADO project (`P33148`, the same prefix already used for `ADO_FEED_SERVER_ID`) and the task's own source (github.com/Checkmarx/ast-azure-plugin: `cxAstScan/task.json`, `services/TaskRunner.ts`) — which caught two real bugs, both the same silent-no-op failure mode (a wrong input name is ignored rather than erroring, so it would've quietly done nothing instead of failing loudly): the input is `CheckmarxService` (capital C, not the lowercase this file had), and `scanTypes` was never a real input at all — `task.json` lists exactly five inputs (`CheckmarxService`, `projectName`, `branchName`, `tenantName`, `additionalParams`), no dedicated scan-type or threshold field among them. `additionalParams` is a raw CLI-flags passthrough, so both now live there: `--scan-types sast` (SAST-only scope) and `--threshold "sast-critical=0;sast-high=0"` (fails on any Critical/High finding; Medium/Low/Info are recorded in the Checkmarx One project but never block the PR). Confirmed via `TaskRunner.ts` this is a real gate, not just a log line: `taskLib.setResult(exitCode == 0 ? Succeeded : Failed, "")`, no middle outcome, and a `--threshold` breach is what makes the CLI exit non-zero. Zero-tolerance on Critical/High with Medium report-only is a starting point, not permanent — third-party plugin code this project doesn't control the style of will have some false-positive rate, and gating on Medium too risked a maintainer just force-merging around a noisy check; revisit once this has run against real submissions.

Also filled in two required inputs this file was missing entirely — `tenantName` (fixed org-wide value, copied as-is) and `branchName` (the working example hardcodes `'main'`; this stage instead derives it from `System.PullRequest.SourceBranch` the same way `TARGET_BRANCH` is already derived in `Validate` above, since this pipeline scans whatever branch a contributor's PR is actually from — this file's own inference, worth confirming on first real run) — and a matching latent bug: the stage's `checkout: self` was missing `persistCredentials: true`, which `Validate` above it already has and explains. `checkmarxService`'s real value (`P33148-CheckmarxOne-SVC`) is filled in too, from the same working pipeline, on the `P33148`-prefix-match reasoning above — a reasonable inference, not a blind guess, but still worth a quick confirmation.

Still open: a final confirmation that the task id itself really is `CheckmarxAST@3` with no space (that's what's in the file, matching the extension's real task id from its own `task.json`, but the working example was cross-checked from a photo of a screen where a search-highlight made that specific detail ambiguous to read with full confidence).

`cleanup-stale-branches-pipeline.yml` staying disabled is now a settled decision, not an open question — explicitly reconfirmed: no branch-deletion pipeline for now. Its dormant code is current (real task name and `githubAppConnection` value) and ready to uncomment if that ever changes, but there's no plan to re-enable it.

Resolved this pass: the leftover `publish-pipeline.yml` debug step that dumped `$HOME/.m2/settings.xml` to the pipeline log right after `MavenAuthenticate@0` injected a token into it has been removed (it wasn't actively leaking anything -- ADO auto-masks `$(System.AccessToken)` -- but it read as troubleshooting residue rather than something meant to stay long-term); `cleanup-stale-branches-pipeline.yml`'s dormant code now matches `publish-pipeline.yml`'s real task name and `githubAppConnection` value; Azure Pipelines' fork-PR secret-withholding behavior has been confirmed against Microsoft's own docs to be functionally equivalent to GitHub Actions' `pull_request` (not `pull_request_target`) semantics — both are opt-in-and-off-by-default at the org/project level, not something this repo's YAML controls, so `validate-pipeline.yml`'s own header now documents this with a citation and flags a one-time check to make in ADO's project settings; the `GITHUB_REPO_SLUG`/`ADO_FEED_URL` pipeline variables have been confirmed as already set in the ADO UI for `publish-pipeline.yml`; the `vmImage: "ubuntu-latest"` TODOs across all pipeline files have been removed — Microsoft-hosted agents are fine for this org, no self-hosted pool needed; and the `SecurityScan` stage's `CheckmarxAST@3` inputs have been cross-checked against both a real working pipeline in the same ADO project and the task's own open-source implementation, which caught two real silent-no-op bugs (`CheckmarxService`, not `checkmarxService`; `scanTypes` was never a real input at all) plus two missing required inputs (`tenantName`, `branchName`) and a missing `persistCredentials: true` on that stage's own checkout; the stage is now also gated on severity via `additionalParams`' `--threshold` flag (fails on Critical/High, reports Medium/Low/Info) — see the Checkmarx paragraph above for the full reasoning.
