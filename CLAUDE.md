# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

INGenious is a Java/JavaFX no-code/low-code test automation IDE (Playwright-Java, Appium, JDBC, JMS/Kafka, SAP), built by ING Bank and open-sourced under MIT (`ing-bank/INGenious`). Full user docs: https://ing-bank.github.io/ingenious-doc/.

## Build & test

This is a multi-module Maven reactor. **`ingenious-api` is not a reactor module** — it's a standalone project that other modules (and all plugins) depend on with `scope=provided`, and must be built and installed to the local `.m2` cache *before* the main reactor:

```bash
mvn clean install --file ingenious-api/pom.xml
mvn clean install --file pom.xml
```

To iterate on a single module without a full reactor build (much faster), build it plus only its required upstream modules:

```bash
mvn -pl IDE -am compile -DskipTests
```

Other useful commands:
- `mvn test` — runs the Surefire test suite (JaCoCo coverage is wired into the same lifecycle).
- `mvn dependency-check:check --file pom.xml` — OWASP dependency vulnerability scan (CI runs this on JDK 11, specifically; the main build runs on JDK 17).
- `mvn versions:display-dependency-updates` — check for outdated dependency versions (`versions-maven-plugin` is available).

**Auto-formatting gotcha**: `prettier-maven-plugin` is bound to the `validate` phase with the `write` goal (see root `pom.xml`), which means **any `mvn` command that reaches `validate` — including a plain `compile` — silently reformats every Java file it touches in place.** If you write/edit a file and then run a Maven command, expect the file's exact byte content (indentation, line-wrapping of long expressions/string concatenations) to change afterward. This breaks exact-string-match tools (e.g. an `Edit`-style diff) if you re-match against what you originally wrote rather than the post-format state — re-read the file (or use line-number/regex-based replacement) after the first `mvn` invocation touches it, not before.

## Module structure

- **Common** — shared build-lifecycle helpers/config for the reactor.
- **Datalib** — backend data source access, data retrieval/transformation.
- **Engine** — core business logic and test-execution workflows; also owns plugin *loading* (`Engine/src/main/java/com/ing/engine/plugin/loader/`).
- **IDE** — the Swing/JavaFX desktop IDE itself; almost all user-facing feature code lives here, under `IDE/src/main/java/com/ing/ide/`.
- **StoryWriter** — BDD scenario/feature authoring.
- **TestData - Csv** — test data / test plan orchestration.
- **Dist** — assembles the final packaged distribution (zip) from the other modules' outputs.
- **ingenious-api** (root-level, non-reactor) — the public contract plugins compile against.

## Code conventions

4-space indent, ~120-char lines, braces always (even single-statement blocks), `PascalCase`/`camelCase`/`UPPER_SNAKE_CASE`. Prefer collection interfaces (`List`, `Map`) over concrete types, Stream API for filtering/mapping, `final` where applicable. INGenious action-naming conventions: storage actions are `store<Data>In<Target>` (e.g. `storeDBValueInDataSheet`), assertions are `assert<Object><Condition>` (e.g. `assertResponseBodyContains`).

The stated convention is no wildcard imports — in practice, existing files (e.g. the whole `pluginmanager` package) use `import java.awt.*;`/`import java.util.*;` throughout. Match the surrounding file's existing import style rather than enforcing the stated rule against it.

## Plugin Marketplace (in progress)

Lives under `IDE/src/main/java/com/ing/ide/main/mainui/components/pluginmanager/`. Lets plugin authors submit a plugin via fork+PR against a separate GitHub registry repo, and lets any user browse/install published plugins — all without ever storing a GitHub PAT: `git`/`gh` manage their own credentials (HTTPS+Git Credential Manager, `gh auth login`), and the IDE never touches either directly for auth.

**Flow**: contributor points Publish at their plugin's source — primarily a GitHub repo+branch link (`cloneContributorSource()` shallow-clones it into a temp dir), or a local folder for quick iteration before pushing anywhere — IDE builds it locally either way to extract manifest metadata and discover actions via reflection → on submit, forks-or-branches the registry repo (based on actual write-access via `gh api .../permissions.push`, not on repo ownership) → opens a PR. A human reviews and merges. CI then independently builds the real artifact, `mvn deploy`s it to an Azure Artifacts Maven feed, and patches the registry via its own auto-merged PR. Install resolves the jar + transitive deps from that feed via Maven.

Contributors are also expected to run their own build+validate pipeline (`docs/plugin-contributor-pipeline-template/`) against their own repo *before* ever pointing Publish at it — but this is a courtesy pre-filter, not a trust boundary the marketplace relies on. The marketplace's own `validate-pipeline.yml` always independently re-builds and re-checks the same source after the PR is opened, regardless of what the contributor's own pipeline already reported, since the marketplace is the one taking the action of deploying to the shared feed afterward and can't base that on a contributor's self-reported pass. This is why the two pipelines' checks are near-identical by design, not an oversight to deduplicate.

**Key files**:
- `PluginRegistryCliService` — all `git`/`gh`/`mvn` process-shelling: fork/branch resolution, PR submission, registry reads, Maven artifact/dependency resolution, `cloneContributorSource()` (read-only shallow clone of a contributor-supplied repo+branch, for the Publish tab's repo-link input — no fork resolution or push, unlike `submitPlugin()`'s own clone of the registry repo), and `saveAdoCredential()` (writes a user-pasted ADO PAT into their real `~/.m2/settings.xml`, preserving anything else already there). `GH_OWN_GIT_CREDENTIAL_ENV` hands gh's own already-verified git credential helper to every network git op in the submission flow — clone, push, and `gh pr create`'s own internal git use — via a scoped `GIT_CONFIG_COUNT` env override (not a persisted git-config change), so the flow depends on exactly one credential source instead of also trusting git's separate credential helper (e.g. GCM) to be configured correctly on the user's machine; the older soft `gh auth setup-git` suggestion is gone now that this is unconditional. `submitPlugin()`'s branch push is `git push --force`, not a plain push — the per-submission branch name (`plugin/<name>/v<version>`) is deterministic, so resubmitting the same plugin+version (routine during manual testing) would otherwise fail as non-fast-forward against the leftover branch from the prior attempt; against a real shared registry with outside contributors, this would also silently clobber any manual follow-up commit someone pushed straight to that PR branch.
- `PluginRegistryConfig` — hardcoded constants (registry repo/branch/path, Maven groupId, ADO org/project/feed/server-id, plus the Reusable Components registry path/sub-path below) — there's exactly one real marketplace, so ordinary users never see or configure any of this; only the ADO PAT is a per-user input.
- `PluginRegistrySettingsDialog` — the config UI, plus a write-only ADO PAT field and a live git/gh/mvn/ADO-credential status panel.
- `PluginManagerService` / `PluginManagerPublishUI` / `PluginManagerBrowseUI` — orchestration and the Publish/Browse tab UIs. Publish's Step 1 offers the repo+branch link as the primary input (backed by `cloneContributorSource()`) with local folder browsing kept as a secondary option; both converge on the same `selectedSourceDir`-based build/metadata/staging flow afterward, so nothing downstream needed to change.
- `docs/plugin-registry-template/` — a copy-paste template for whatever repo ends up being the real registry, plus its own setup README. **GitHub Actions hosted runners are not available for this org** (confirmed via a hard error, not just a preference) and installing the Azure Pipelines GitHub App yourself isn't allowed either (that's an org-admin action, done automatically for repos created within the company) — so the `.github/workflows/validate.yml`/`publish.yml` pair is kept only as reference; the CI actually in use lives in `ado-pipelines/` (`validate-pipeline.yml`, `publish-pipeline.yml`, `cleanup-stale-branches-pipeline.yml`), triggered by Azure Pipelines' native GitHub PR/push integration instead. `ingenious-api` is deliberately *vendored* as a jar in this template (`ci/vendor/`) rather than resolved from ADO, specifically so the PR-time pipeline stays credential-free to safely build fork-PR'd code — that reasoning holds regardless of which CI system runs it.
- `docs/plugin-contributor-pipeline-template/` — **active**, not parked (an earlier fully-decentralized design here — contributor pipeline does build+validate+publish, marketplace never builds at all — was considered and explicitly rejected: the marketplace still needs its own independent validate before it deploys under its own authority). What this template actually does now: build + the same checks `validate-pipeline.yml` runs (required files, README length, groupId, build, manifest), and nothing else — no ADO credentials, no feed access, no registry-repo/GitHub-App dependency at all. Runs entirely on the contributor's own repo/ADO project, decoupled from the marketplace's infrastructure. Its only purpose is catching obviously-broken submissions before they cost the marketplace a CI run or a reviewer's attention — passing it doesn't skip or shortcut `validate-pipeline.yml`, which always re-runs independently once the contributor submits via the IDE.

## Reusable Components Marketplace

Same submission mechanism as the Plugin Marketplace (same repo, same review-gated PR flow), deliberately simpler: a Reusable Component is just data (a Shared scenario's test-case YAML files — `Datalib/.../component/io/YamlTestCaseStore`), never compiled, so there's no build, no Maven coordinates, no version, and no Azure Artifacts feed at all — GitHub-repo-only, which is why this only needed a validate pipeline, no publish/deploy pipeline and no contributor-pipeline-template equivalent (the source is always already-local, never a separate repo+branch to pre-check).

**What's shared vs. new**: `PluginRegistryCliService` gained two generalized methods so the actual git/gh mechanics aren't duplicated — `submitToRegistry()` (the fork/branch/PR submission mechanism `submitPlugin()` now delegates to, parameterized by target sub-path instead of hardcoding `plugins/`) and `fetchFileFromRegistry()` (same generalization for `fetchRegistryJsonRaw()`), plus a new `listRegistryDirectoryRaw()` (Reusable Components have no Maven artifact to resolve on install, so installing means listing and copying whatever files a component actually has). Everything Maven/ADO-shaped (`buildLocally()`, `resolvePluginArtifact()`, `saveAdoCredential()`, the groupId check) stayed exactly where it is — untouched, and not something a Reusable Component has an equivalent of.

**Key files**: `ReusableComponentEntry` (name/displayName/description/author/authorEmail/tags/dateAdded/featured — no `entryClasses`/Maven coordinates/version) · `ReusableComponentCliService` (thin — composes `PluginRegistryCliService`'s generic methods) · `ReusableComponentService` (mirrors `PluginManagerService`'s shape: `fetchRegistry()`, `listLocalSharedComponents()` for the Publish picker, `stageSubmission()`, `installComponent()`) · `ReusableComponentManagerUI` (Browse/Publish tabs, opened in a standalone dialog via `openBrowseDialog()`/`openPublishDialog()`) · `SharedReusablePopupMenu` (`SharedReusableTree.java`) — "Publish to Marketplace..." on a right-clicked scenario, visible only in the scenario context.

**The one real mechanical difference from plugins**: there's no merge-time bot pipeline for this artifact type to patch a registry file after the fact, so `reusable-components.json` gets updated *inside the contributor's own PR* (`ReusableComponentService.buildUpdatedRegistry()` computes it, `submitComponent()` commits it alongside the component's own files via `submitToRegistry()`'s `additionalFiles` param — a repo-root file living outside the component's own sub-path, committed in the same branch). Since that diff is contributor-supplied rather than bot-patched, `validate-reusable-component-pipeline.yml`'s last check exists specifically to verify it only adds-or-updates the submitter's own single entry — the thing that earns trust for a self-supplied registry edit that would otherwise be a plugin-side no-no (per CLAUDE.md's own "never trust self-reported data over what's actually verified" pattern elsewhere in this file).

**Not yet wired**: a standalone "Browse Marketplace..." entry point for installing without first publishing something (right now `ReusableComponentManagerUI`'s Browse tab is only reached via the dialog `openPublishDialog()` opens, which does include a Browse tab, so this is a minor discoverability gap, not a missing capability) — a natural home is `TestDesignUI`'s Shared Reusable Components panel, not yet investigated closely enough to wire up safely.

**Current state**: publish (opens a real PR), browse (reads a real `registry.json`), and install (resolves a real jar from ADO Artifacts) are all built and have been manually exercised end to end against the marketplace's own registry repo (working off a `registry-branch` rather than its default branch — repo identity itself is deliberately not tracked in this file, it's config, not architecture) and a real company ADO feed. The CI pipeline piece (`ado-pipelines/`) has moved past placeholder values for `validate-pipeline.yml` and `publish-pipeline.yml`, and `publish-pipeline.yml` has been confirmed to run successfully end to end (GitHub App auth + deploy to the feed) — see the GitHub App task section below for what's still outstanding (`cleanup-stale-branches-pipeline.yml` in particular).

**Known gotchas from manual testing**:
- **ADO Artifacts has no Maven-publish path via `az` CLI.** `az artifacts` only supports Universal Packages (a different, incompatible package type/protocol from what `resolvePluginArtifact()` resolves) — publishing a real Maven artifact only ever happens via `mvn deploy`, never `az`.
- **Two different ADO PAT scopes matter and are easy to conflate**: the one in `~/.m2/settings.xml` (managed by the app via `saveAdoCredential()`) is deliberately **Packaging: Read** only, for installs. A manual `mvn deploy` test needs a separate **Packaging: Read & Write** PAT under a different `<server>` id — trying to deploy with the read-only one fails with 401, by design, not a bug.
- **`-DaltDeploymentRepository=...` on the command line is fragile** across shells (line-continuation characters differ between bash/zsh and PowerShell; a dropped `-D` prefix manifests as a confusing "could not resolve plugin/artifact" error, not an auth error). For one-off manual deploys, temporarily adding `<repositories>`/`<distributionManagement>` to a *scratch copy* of the plugin's `pom.xml` sidesteps this — never commit that into `plugin-examples/helloworld/pom.xml` itself, since contributor plugin POMs are meant to stay infra-agnostic.
- **`ADO_FEED_SERVER_ID`-style values have to match in two separate, independent places — easy to conflate since both are called "server id" and both default to a similar-looking string.** (1) *Install side, in the IDE*: `AppSettings.ADO_FEED_SERVER_ID` (Registry Settings' "Maven server id (internal label)" field, default `ado-plugin-feed`) is used identically as the `<repository><id>` in the generated shim pom and in every `-DremoteRepositories=<id>::default::<url>` CLI arg (`PluginRegistryCliService.resolvePluginArtifact()`/`resolvePluginDependencies()`). It only has to match the `<id>` of a `<server>` entry in the *user's own local* `~/.m2/settings.xml` (the one `saveAdoCredential()` writes) — it does **not** need to equal the real Azure Artifacts feed name; it's a purely local bookkeeping key, independent of Registry Settings' separate "Feed name" field. (2) *Publish side, in `publish-pipeline.yml`*: the `ADO_FEED_SERVER_ID` variable has to match whatever `MavenAuthenticate@0`'s `artifactsFeeds` input resolves to as a `<server><id>` — and `artifactsFeeds` is *not* a free label, it has to be the real feed's actual name in ADO, since that's what the task authenticates against. So inside that one pipeline, `ADO_FEED_SERVER_ID` == `artifactsFeeds` == the real feed name, or the deploy step's `-DaltDeploymentRepository` can't find matching credentials. These two matching-groups don't technically have to equal each other, but `publish-pipeline.yml`'s own inline comment recommends keeping the IDE-side value and the pipeline-side value identical anyway, purely so there's one string to remember instead of two.

**CI pipelines — architecture settled, wiring now mostly filled in**: GitHub Actions is unavailable outright (hosted runners disabled org-wide), so PR-time validate and merge-time publish both run on Azure Pipelines (`docs/plugin-registry-template/ado-pipelines/`), triggered via Azure Pipelines' own GitHub PR/push integration rather than `.github/workflows/`. A fully-decentralized alternative (contributor pipeline does build+validate+publish, marketplace never builds at all) was considered and explicitly rejected — see `docs/plugin-contributor-pipeline-template/` above for why the contributor template stays a courtesy pre-filter instead of replacing this centralized validate/publish pair.

Two things changed from the original GitHub-Actions-only design, beyond just moving where the YAML runs:
- The merge-time deploy step uses `MavenAuthenticate@0` + `$(System.AccessToken)` for the ADO feed (reusing the team's existing INGenious-build pipeline pattern) — no `ADO_PAT` secret to own/rotate.
- All GitHub-side write operations — the registry-patch push+PR in `publish-pipeline.yml`, the PR-listing+branch-deletion in `cleanup-stale-branches-pipeline.yml` — go through the **`GitHubAppToken@1`** task instead of a GitHub PAT, since a standing PAT for this isn't allowed. It exchanges the org's installed GitHub App connection for a short-lived (~1hr) installation token, consumed via `GH_TOKEN` for `gh` CLI calls. (This was previously unreconciled against an alternate name, `create-github-app-token@1` — `GitHubAppToken@1` is the one actually wired into `publish-pipeline.yml` now, with a real `githubAppConnection` value. `cleanup-stale-branches-pipeline.yml` is currently disabled — see below — and still has the old name in its dormant code, worth fixing before it's ever re-enabled.)

**Confirmed working**: `docs/plugin-registry-template/ado-pipelines/diagnostic-github-app-token-test.yml`, a throwaway diagnostic pipeline, ran end to end against a repo with the GitHub App connection enabled — the token task resolved, the `githubAppConnection` connection resolved, and the resulting installation token has both read and write access (verified by creating and immediately deleting a real branch via the GitHub API). This settled what was previously the biggest open risk in this design, and the resolved task name and a real `githubAppConnection` value have since been copied into `publish-pipeline.yml`, alongside a real `ADO_FEED_SERVER_ID` — and `publish-pipeline.yml` itself has since been confirmed to run successfully end to end (both the GitHub App auth and the feed deploy). `cleanup-stale-branches-pipeline.yml` still has the old task name and a literal TODO placeholder for `githubAppConnection`, but that whole file is currently commented out end-to-end (deliberately disabled, matching an earlier ask to hold off on any branch-deletion pipeline), so it hasn't needed updating yet. The diagnostic pipeline/file itself is disposable once `cleanup-stale-branches-pipeline.yml` is brought current and re-enabled.

The GitHub App connection is enabled automatically on repos **created within the company**, not on personal ones — this was the reasoning for testing the token mechanism against a separate company-created repo early on, back when the day-to-day registry repo was still a personal/workaround stand-in without that connection. That's no longer the setup: the registry repo in use now was made directly for the marketplace, not a personal fork, so this constraint no longer limits what's testable here.

Still open: agent pool (`vmImage: "ubuntu-latest"` with a TODO to swap in an org pool if Microsoft-hosted agents aren't allowed) in all three files; whether the `GITHUB_REPO_SLUG`/`ADO_FEED_URL` pipeline variables `publish-pipeline.yml` expects have actually been set in the ADO UI (deliberately not in the YAML itself, so the file alone can't confirm this either way); and bringing `cleanup-stale-branches-pipeline.yml` current (old task name, placeholder `githubAppConnection`, still fully commented out) before it's ever re-enabled. Also still unconfirmed: whether Azure Pipelines' fork-PR secret-withholding behavior actually matches GitHub Actions' — needed before treating `validate-pipeline.yml` as safe against untrusted fork PRs.

There's also a leftover debug step in `publish-pipeline.yml` ("Inspect Maven settings") that dumps `$HOME/.m2/settings.xml` to the pipeline log right after `MavenAuthenticate@0` injects a token into it — ADO auto-masks `$(System.AccessToken)`, so this likely isn't actively leaking anything, but it reads like troubleshooting residue rather than something meant to stay long-term.
